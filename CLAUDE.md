# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

BSc thesis (BME): text-to-SQL with a local LLM (Ollama, `qwen2.5-coder:7b`) translating natural-language questions — mostly **Hungarian** — into PostgreSQL queries — main dataset: Brazilian **Olist e-commerce**, but databases are swappable (see Datasets) — and **measuring the effectiveness** of different approaches. Planned extensions: RAG, MCP, fine-tuning, more languages, more validation, natural-language answers. Console output is in Hungarian; keep that convention.

Because the thesis is about measurement, changes that affect what the model sees (prompt text, schema text, dataset hints, LLM options) change results and must be treated as a new experimental configuration, not a refactor.

## Environment & commands

Windows machine; use the project venv (`.venv\Scripts\python.exe`). `pip install -r requirements.txt`.

Runtime services:
- **PostgreSQL** (`docker compose up -d`, container `text-to-sql-postgres`, `./datasets` mounted at `/datasets`), one database per dataset. The app connects as the read-only role `text2sql_reader`; server/credentials from `TEXT2SQL_DB_*` env vars (see `src/database.py`), the database name from the dataset.
- **Ollama** with `qwen2.5-coder:7b` pulled.

## Datasets

A dataset = one folder in `datasets/<name>/` (`dataset.json` with `db_name`, `schema.sql`, `import.sql`, optional `hints.txt`, optional `attacks.json`, `test_cases/<language>.json`, gitignored `data/`); details in `datasets/README.md`. Selected by `--dataset` or `TEXT2SQL_DATASET` (default `olist`); `f1` is the second real dataset (Formula 1, 17 tables, snake_case columns renamed from the camelCase CSVs); `adventureworks` is the large-schema dataset (68 tables in 5 PostgreSQL schemas, ~4.8k prompt tokens; built from Microsoft's CSVs + a pinned community port, see its `SOURCES.md`); `sales` is a toy smoke-test/template. A dataset's tables live in `public` unless `dataset.json` lists `schemas`; `schema.py` then shows them schema-qualified (`sales.customer`) and only base tables, never views, while `public` tables keep bare names so older datasets' schema text (and hashes) are unchanged. `setup_dataset.py` grants the reader role on every listed schema. Test-question language is selected by `--language` or `TEXT2SQL_LANGUAGE` (default `hu`); only the questions are translated, the prompt stays the same. A translation must be identical to `hu.json` except for `question` (same ids, order, ground truths), otherwise results across languages are not comparable. `src/dataset_loader.py` is the only code that knows the folder layout (deliberately not named `datasets.py`, which would shadow the Hugging Face package). Nothing dataset-specific belongs in `src/`.

Setup: `python database/setup_dataset.py <name> [--recreate]` runs psql in the container: create DB → `schema.sql` → `import.sql` → `database/readonly_role.sql` (psql var `db_name`; one `text2sql_reader` role for the server, SELECT-only, read-only transactions, 10s timeout). `src/tests/test_datasets.py` checks every dataset folder is complete (including a default-language test file), every language's ground truths pass the structural validator, and translations differ only in `question`.

Run from the repo root:
- Demo: `python src/main.py ["kérdés"] [--dataset <name>] [--no-answer] [--rag] [--schema-retrieval full|bm25|dense|hybrid] [--translate-for-retrieval] [--column-values] [--retrieval-k N] [--table-selection]` (default question is for Olist; prints the selected tables when retrieving)
- Evaluation: `python src/evaluation/evaluator.py --run-name <name>` (also `--dataset`, `--language`, `--answer`, `--correction-rounds`, `--rag` (= `pipeline.RAG_SETTINGS`, overrides the retrieval switches), `--no-schema-hints`, `--column-values [--column-values-max 50]`, `--schema-retrieval full|oracle|bm25|dense|hybrid` with `--retrieval-k 5`, `--no-fk-expansion`, `--retrieval-descriptions`, `--translate-for-retrieval`, `--table-selection [--selection-style strict|inclusive] [--selection-keep-top N]`, `--embedding-model`, `--model`, `--temperature`, `--seed`, `--num-ctx`, `--no-function-blocklist`, `--cases` which overrides the language file). Each run writes a new file `src/evaluation/results/<timestamp>_<dataset>-<language>_<model>_<name>.json` (older results lack the language or the dataset in the name) with the full `PipelineConfig`, git commit/dirty flag, model digest, prompt/schema/test-case hashes and the exact schema text. `qwen_baseline.json` is the old-format v1 result.
- Repeated runs: `python src/evaluation/run_batch.py --run-name <name> [--datasets ...] [--languages ...] [--repeats 3]`; unknown options (e.g. `--correction-rounds 2`) are passed to every evaluator run. Refuses to start with uncommitted changes unless `--allow-dirty`. Runs round by round, then prints mean ± std per dataset/language/setup and writes `results/<timestamp>_batch_<name>.json`. `python src/evaluation/report.py <result files or globs>` does the same summary for any existing runs and warns when grouped runs differ in prompt/test-set/schema hash or model digest. The evaluator's `git.dirty` ignores `src/evaluation/results/`, so result files of earlier runs do not mark later runs dirty.
- Retrieval evaluation (no answer LLM, seconds): `python src/evaluation/retrieval_eval.py --retriever bm25|dense|hybrid --run-name <name>` (also `--datasets`, `--languages`, `--k 1 2 3 5 8 10`, `--ngram 3` (0 = whole words), `--descriptions`, `--max-hops 2`, `--embedding-model bge-m3`, `--translate` (questions translated by the SQL model first, cached in `.cache/translations/`); dense/hybrid need `ollama pull bge-m3`). Ranks every test question's tables and reports, per top-k with and without FK expansion, the share of questions whose needed tables (from the ground truth) were all found, recall and tables shown; writes `results/<timestamp>_retrieval_<retriever>_<name>.json` with per-question rankings.
- Attack evaluation: `python src/evaluation/attack_evaluator.py --run-name <name>` (also `--dataset`, `--no-function-blocklist`). No LLM: runs the dataset's hand-written `attacks.json` SQL through the defence layers one by one (same order as `validate_sql`, then execution as the read-only role) and records which layer stopped each; writes `results/<timestamp>_<dataset>-attacks_<name>.json`. `test_datasets.py` checks the offline-layer expectations of `attacks.json`; the database layers are only checked by this runner.
- Tests: `python -m pytest` (config in `pyproject.toml` puts `src/` on the path; tests import modules flat, e.g. `from llm import extract_sql`). Offline only: `python -m pytest -m "not db"`. Single test: `python -m pytest src/tests/test_comparison.py -k relaxed`.

## Architecture

`pipeline.run_pipeline(conn, question, schema, PipelineConfig)` is the single code path used by both `main.py` and the evaluator: generate → validate → execute (invalid SQL is never executed) → if validation or execution failed, up to `max_correction_rounds` corrections. It returns a `PipelineResult` (top-level fields = final attempt, tokens/timings = totals, `attempts` = every try) and prints nothing; front-ends (CLI, evaluator, future MCP server) only format it.

`PipelineConfig` holds every feature switch; defaults reproduce the baseline (correction off in the evaluator; `main.py` demo uses 2 rounds). New features get a switch here, off by default, and only once they actually work. Connection and schema must come from `pipeline.open_connection(config)` / `pipeline.load_schema(conn, config)` so database, schema text and hints all match `config.dataset`.

- Final RAG configuration: `pipeline.RAG_SETTINGS` (dense bge-m3 retrieval, `retrieval_k` 10, FK bridges, strict `table_selection`), applied by `--rag` in the demo and the evaluator; chosen on AdventureWorks (100 questions: full schema 53% → 61% relaxed EX, oracle 80%); keep-top and the inclusive prompt did not measurably help. Column values are a separate switch, not part of it.
- Schema retrieval (switch: `schema_retrieval`, `SCHEMA_RETRIEVAL_MODES`): `full` (baseline) lists every table; `oracle` lists only the tables the question's ground truth reads (`sql_tables.tables_in_sql`, CTE names excluded) plus relationships between them — an evaluation-only upper bound, built per question by the evaluator via `load_schema(conn, config, tables=...)`; the model still never sees the ground truth. `bm25` / `dense` / `hybrid` use a `retrieval.SchemaRetriever` built once per dataset by `pipeline.make_schema_retriever(conn, config)` and passed to `run_pipeline(..., retriever)`, which selects `retrieval_k` tables (+ FK bridges if `retrieval_fk_expansion`) per question and builds the schema text from them. `translate_for_retrieval` translates the question with `llm.translate_question` (`TRANSLATE_TEMPLATE`, hashed) for the search only — the SQL model still gets the original question. `table_selection` (schema linking, needs a retrieval mode, use with a larger `retrieval_k` such as 10) asks the SQL model with `TABLE_SELECTION_TEMPLATE` (hashed) to keep only the needed candidates (`retriever.describe` lists names + columns), parses its answer with `retrieval.parse_table_choice` (qualified names, or bare names when unambiguous) and re-adds FK bridges with `retriever.expand`; an answer naming no candidate keeps them all. `table_selection_style` picks the prompt from `llm.TABLE_SELECTION_TEMPLATES` (`strict`, or `inclusive`: keep a table when unsure and keep tables holding names / descriptive values; each hashed in `TABLE_SELECTION_PROMPT_SHA256S`); `selection_keep_top` N keeps the top N retrieved candidates whatever the model drops. `PipelineResult` records `schema_tables`, `retrieval_query`, `translation`, `candidate_tables`, `table_selection`; timings get `retrieval_s` / `translation_s` / `selection_s`; evaluator results add `candidates_complete`. Every evaluator result records `gold_tables`, `schema_tables` (None = all), `table_recall` and `tables_complete`.
- `retrieval.py` (not yet wired into the pipeline): `TableDoc` per base table (name, columns, optional COMMENT descriptions — only AdventureWorks has them; `repair_mojibake` fixes the port's Latin-1-loaded comments), `BM25Retriever` (own Okapi BM25, k1 1.5, b 0.75, over character n-grams so one-word identifiers like `salesorderheader` still match; ties broken by name, so rankings are deterministic), `EmbeddingRetriever` (cosine over Ollama embeddings of `TableDoc.prose`; multilingual `bge-m3` matches Hungarian questions to English tables; table vectors cached in gitignored `.cache/embeddings/`, keyed by model digest + texts), `HybridRetriever` (Reciprocal Rank Fusion, c = 60), `foreign_key_graph` and `expand_with_bridges` (adds tables on a shortest FK path of at most `max_hops` between two selected tables). Catalog comes from `schema.fetch_catalog`, the same query as the prompt's schema text.
- Column values (switch: `column_values`, `column_values_max` 50): `schema.fetch_column_values` lists every distinct value of text columns with at most that many values (none longer than 40 chars) after the column in the schema text (`- order_status character varying (values: 'approved', 'canceled', ...)`), so the model writes categories as stored. One query per text column, cached per database in-process (the schema text is rebuilt per question when retrieving). Puts real data in the prompt. Off = byte-identical schema text.
- Embeddings run on the CPU (`retrieval.EMBEDDING_OPTIONS = {"num_gpu": 0}`): on the 6 GB GPU the SQL model (~5.4 GB, ~79% on GPU even alone) and bge-m3 evicted each other per question (~6x slower runs). CPU vs GPU vectors give the same aggregate retrieval metrics but a few near-tie rank swaps; the device is part of the embedding cache key.
- `schema.py` builds the prompt's schema text from `information_schema.columns` plus FK relationships from **`pg_catalog.pg_constraint`** (not `information_schema.constraint_column_usage`, which hides FKs from non-owner roles like `text2sql_reader`), then appends the dataset's `hints.txt` (switch: `schema_hints`).
- `llm.py`: `PROMPT_TEMPLATE` (hashed into `PROMPT_SHA256` for results; dataset-independent, dataset-specific guidance goes in `hints.txt` — an Olist-only line in the template used to push the model toward "product categories" on other datasets), `LLMSettings` (temperature 0, fixed seed, explicit `num_ctx` because Ollama silently truncates longer prompts), `extract_sql` for code-fence stripping. `correct_sql` continues the same conversation (baseline prompt, the failed answer, `CORRECTION_TEMPLATE` with the Postgres error), so the first-attempt prompt is unchanged; both templates are hashed into results. Determinism: run alone, repeated runs were practically identical (18 runs × 3 repeats: at most 1 question differed), but two evaluations hitting Ollama at the same time made results diverge (3 of 50 questions) — run measurements one at a time and do not use Ollama meanwhile. The uncertainty therefore comes from the number of questions (95% CI about ±13 points at 50 questions), not from repeats: report confidence intervals and paired McNemar tests per question rather than repeat standard deviations.
- Natural-language answer (switch: `natural_language_answer`, off in the evaluator, on in the demo): after the final attempt executed, `llm.generate_answer` sends question, SQL, column names and at most `answer_max_rows` rows in a separate conversation with `ANSWER_TEMPLATE` ("answer in the question's language"; no language detection). It never changes the SQL, so EX metrics are unaffected; the answer is stored but not scored. Its tokens stay in `PipelineResult.answer` (not added to the SQL token totals), its time in `timings["answer_s"]`.
- Validation, combined in `sql_validator.validate_sql(conn, sql)`; the order matters because stage 3 interpolates SQL into `PREPARE`:
  1. `sql_structural_validator.validate_sql_structure(sql)` — offline sqlglot check: one statement, a `Query`, no DML/DDL anywhere in the tree, no `SELECT INTO`, no locking clauses. Does not filter functions.
  2. `sql_function_validator.validate_sql_functions(sql)` — offline name-based blocklist (`BLOCKED_FUNCTIONS`, grouped by reason) over sqlglot `exp.Anonymous` nodes. Switch `block_functions` is **on by default**, a deliberate exception to "off by default": it is a safety guard, does not change what the model sees, and blocks no ground truth. A blocklist is never complete; it is defence in depth, not the boundary.
  3. `sql_schema_validator.validate_sql_schema(conn, sql)` — `PREPARE`/`DEALLOCATE` so Postgres checks names and types without executing.
- Security relies on the DB role, not the validators. `database.execute_query` and the validators always **roll back** (never commit), so session changes made by a generated query (e.g. `set_config`) cannot leak into the next question.
- `evaluation/comparison.py` defines the metrics: **strict EX** (same rows and columns) and **relaxed EX** (all ground-truth columns present among generated columns, extra columns allowed). Row order counts only if the ground truth has a top-level `ORDER BY`; numbers are rounded to 4 decimals. Durations (intervals) compare as days. A test case may list `alternative_sql` (further correct answers, e.g. the 9 Olist category questions also accept Portuguese names; checked 1:1 against the English ones); `comparison.match_any` accepts the first that matches, results record `matched_ground_truth` (0 = ground truth). Oracle tables and table recall still use the ground truth only. The evaluator executes all ground truths before calling the LLM and fails fast if one is broken. Since correction only runs after a failed first attempt, a run with correction also reports `first_attempt` metrics, i.e. the same run without correction.
- Olist pitfall: `customer_id` is per order; a real customer is `customer_unique_id`.
